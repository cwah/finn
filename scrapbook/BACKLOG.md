# Backlog

Feature requests and ideas for the scrapbook. Anything here is a **candidate, not a
commitment** — the build phases in `CLAUDE.md` are the actual plan, and this is the pile
of things we might pull into one.

Add an item as `- [ ] What it is — why, and anything that constrains it`. Move it under
Shipped when it lands. No ceremony beyond that.

## Ideas

- [ ] **Suggested weekly prompts.** Proactively message user via Telegram bot on a weekly 
      basis to add to scrapbook. Prompt should be generated by LLM based on baby's age and
      recent posts. Add corresponding new card type that is a question and answer format.
- [ ] **Time based posts.** Optionally use time in addition to date.
      Prepopulate from the earliest photo corresponding to the date
      selected. Make selecting this optional.
- [ ] **Location.** Use photo metadata to infer location. Also allow 
      users to manually set location. Have location preselected and 
      enabled by default.
- [ ] **Loop motion photos.** Automatically loop motion photos in the
      viewer. Don't show the video progress bar and only have a play/
      pause button, similar to the main page
- [ ] **Gesture based swipes.** Use gestures on photos/media to swipe
      through photos on viewer. Have photos follow the swipe, not
      just be an animation. Use dots below the photo to indicate
      which photo/progress.
- [ ] **Paused motion photos.** When you pause a motion photo, reset
      to the main frame.
- [ ] **Download the cropped image.** Right-click → Save Image currently saves the
      *uncropped* original, because the crop is applied at render (CSS offsets inside an
      overflow box) and never exists as a file. Saving what you can see needs a real
      cropped file — either drawn client-side onto a canvas and offered as a download, or
      produced server-side as a derived image. The latter overlaps Phase 3's optimisation
      pipeline, so it may be worth waiting and doing both at once. Note this is a
      consequence of the non-destructive design, not a bug in it: the whole original is
      deliberately kept.
- [ ] **Inline metadata editing via Telegram posts.** Support certain post settings to be
      configured inline when creating a post, including modifying the date of the post.

- [ ] **Move video encoding off the device.** The display copy is produced ON THE PHONE,
      in real time, by playing the clip through a canvas into `MediaRecorder`
      (`js/video-encode.js`). That costs roughly the clip's own length in wall time before
      a post can be saved, holds the compose sheet open throughout, and competes with
      whatever else the phone is doing — and a 3+ minute clip did not merely crawl, it
      failed outright. `MAX_CLIP_SECONDS` was cut from 60 to 30 as the interim answer, so
      the cap is currently a property of the slowest plausible phone rather than of what a
      memory should be.
      Encoding server-side would let the cap go back up (or away), take the wait out of
      saving, and produce better files than a canvas pipeline can — but PocketBase's
      container has no ffmpeg, the work is CPU-heavy on an instance sized for serving a
      family scrapbook, and it needs somewhere to put the original while it waits. Worth
      pricing against a queue plus a worker, or a hosted transcoding service. Overlaps
      **Transcode HEVC on upload** below and Phase 3's optimisation pipeline; if any of
      this is built, build it once.

- [ ] **Transcode HEVC on upload.** iPhones record `hvc1` (H.265) by default, and
      `assets/sample-clip.mp4` is one. Chrome reports `canPlayType` as "probably" on Apple
      hardware, but HEVC support is uneven across browsers and machines in a way H.264 is
      not — a memory that plays on one parent's phone and not the other's is the failure
      that matters here. Belongs with Phase 3's optimisation pipeline: transcode to H.264
      (and move `moov` to the front while there, so playback can start before the whole
      file arrives).

- [ ] **Object storage for media.** Researched 2026-08-31 and deliberately NOT done, so
      the question does not get re-opened from scratch. Render DOES have a native
      S3-compatible object store, but it has been in **alpha behind a waitlist since March
      2026** and there is no GA entry in the changelog as of August — not somewhere to put
      irreplaceable memories, and not something that can simply be switched on.
      The other one-provider option is the MinIO template, which is S3-compatible and runs
      on Render — but it stores objects on a Render SSD disk with daily snapshots, which is
      precisely what PocketBase's own disk already is. That trades a second service, a
      second bill and an extra hop between PocketBase and its files for no gain in
      durability. It is strictly worse here.
      So the trigger for revisiting is CAPACITY, not durability: the disk enlarges but
      never shrinks, and the two-copy video scheme pushes usage up. Revisit when the 5 GB
      is genuinely in sight, or when Render's own object storage reaches GA.

- [ ] **Re-encode video on upload.** Deferred deliberately, with the numbers measured
      2026-08-30: 17 stored clips came to 157 MB, and two of them — 58.8 MB/24s and
      46.4 MB/8.8s — were two thirds of that. So the win is real but concentrated in a
      couple of long 4K clips, and the 200 MB field limit keeps it from running away.
      What was established while looking, so it need not be re-derived:
      `MediaRecorder.isTypeSupported('video/mp4')` is TRUE on current Chrome, so H.264
      MP4 can be produced with the browser's own muxer — no hand-written byte-level
      muxing, which is what makes this tractable at all. The cost is that MediaRecorder
      runs in REAL TIME and needs the tab in front: a 24s clip takes 24s. Encoding only
      the trimmed stretch would fix both the time and the size at once, but would make
      the trim destructive, which is against how framing works everywhere else here.
      WebCodecs is faster but needs an MP4 muxer written by hand, and a subtle bug there
      is an unplayable memory rather than an obvious error.
      Pairs naturally with the HEVC item above — both are "re-encode on the way in".

- [ ] **The expanded video shows the untrimmed length.** Playback *is* trimmed — it starts
      at `trimStart` and `holdToTrim` stops it at `trimEnd` — but the native `<video
      controls>` scrub bar spans the whole source file, so a 17s clip trimmed to 13.9s
      still reads "0:17" and the handle can be dragged past the end. The control bar is
      the browser's, and its extent cannot be restyled or clipped. Fixing it means
      replacing it with our own transport (play/pause, a scrub bar drawn over the trimmed
      range, elapsed within the trim), which is worth doing once — the cards would share
      it. Alternatively, Phase 3's pipeline could store a genuinely cut derivative
      alongside the original, which would also fix right-click-save; the original stays
      whole either way, so the trim remains re-editable.

## Shipped

- [X] Notify subscribers of new posts - Add functionality to allow 
      other viewers to subscribe to new posts. Consider a simpler web hook to share on a timeline or feed somewhere.
- [x] Downscale photos for display on upload (2560px long edge), and serve sized
      thumbnails to the compose strip, the framing surface and the timeline cards rather
      than full-size originals.

- [x] Pick up memories added elsewhere — an open scrapbook now polls for posts made by the
      bot or by the other parent, and slots them in without a reload. Only while the tab
      is visible, and immediately on coming back to it. Arriving cards never shove what
      you are reading.

- [x] Telegram bot access — allow users to upload and add new posts via Telegram bot.
- [x] Pause a motion photo — a hover-revealed button on the card, which stays visible
      while it is holding the loop still. The pause outlasts scrolling away and back.
- [x] Video and motion photos — a clip travels as an ordinary photo with a poster frame,
      so the engine, the crop box and every layout rule are untouched. Trimming is
      non-destructive like cropping (the file keeps every frame), capped at a minute;
      motion photos loop on screen and videos wait for a tap. Live Photos are paired from
      the two files iOS shares, and Google motion photos are split out of the jpeg.
- [x] Rotation — stored as degrees and applied at render, for photos and video alike.
      A quarter turn changes the card, because the engine reads the shape a photo
      presents; the crop and focal point turn with it.
- [x] Photo cropping — non-destructive crop rectangle stored per photo and applied at
      render; cropped dimensions drive the layout, so cropping wide-to-tall really does
      turn a card portrait. Original file never altered.
- [x] Editing — the pencil on your own posts reopens the compose sheet prefilled;
      caption, date, milestone and photos are all editable, plus delete. Author-only,
      enforced in PocketBase rules rather than just hidden in the UI.
- [x] Photo carousels — more than four photos becomes a swipeable carousel with dots,
      rather than a grid nobody can see anything in.
- [x] Image handling — smart focal point picked at capture with a drag-to-reframe
      override, "make main photo" to choose what leads a post, and tap-to-open at full
      aspect ratio.
- [x] Phase 2 — PocketBase: schema in `pb_migrations/`, one account per parent, photo
      upload to local disk, and a data layer that still swaps back to mock with one line.
- [x] Single entrypoint — one floating `+` opens the compose sheet; photos are attached
      from inside it. Replaced the two-button tray, and the bottom bar is gone with it.
- [x] Compose sheet — caption, memory date, and an optional milestone on capture.
- [x] Date a new post from the media attached to it, when every item agrees on a
      day. Said out loud under the field, and never applied while editing or over a
      date typed by hand.
- [x] Parallax fade in/out of milestone art — the artwork is fixed to the viewport and
      never moves; `centreProgress()` maps the card's position to an opacity, so it fades
      up as the card arrives, is clearest when the card owns the screen, and fades away
      as it leaves.
- [x] Milestone sketches beside the card, alternating sides (some artwork pinned to one
      side), never repeating back to back.
- [x] Right-edge date scrubber, Google Photos style.
- [x] Light pastel sage-and-blue palette.
